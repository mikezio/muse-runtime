The background checklist. A worker runs it about every 30 minutes. Each tick runs the checks below; a quiet tick with verified checks is a fine tick. Do what the worker can do itself; record the rest with its evidence. The file holds only the checklist itself, never run results.

- Read the user's proactive preferences at the start of every tick and honor them as written. Standing prefs batch non-urgent items; they never override a live instruction. When instructions conflict: runtime safeguards and approval limits win. Below them, the user's current explicit instructions beat any stored instruction. Stored operating rules hold durable conventions; this checklist holds routine duties. Never invent urgency categories, quiet hours, or notification exceptions.
- Check recent cron runs (last 48h, user-owned jobs) for failures. If a job is failing, figure out why and fix it if you can; otherwise record a concrete repair proposal with the evidence. Stateful via a helper: `observe` records the observation only (never retries, never advances backoff, never moves the due time, even when a retry is due). When a retry is due, the worker performs the permitted repair itself, then records it under a stable operation id so replays are idempotent. Surface once per unique finding via a content fingerprint. Resolve only on observed resolution.
- Anything time-sensitive in the next hour, or genuinely new and worth the user's attention: prep it yourself or start the work. "Known" is not "resolved": a recurring failure still gets surfaced, with the plan to fix it. Only interrupt for genuinely new and useful things.
- If a session the agent depends on is dead, or something needs the user (a login code, an approval, a decision that's theirs), surface it. Otherwise stay quiet.
- Keep helper daemons alive: check, restart, verify. Note restarted/still-down in the tick report.
- When a finding implies action, do the feasible part now. What's beyond worker reach gets recorded with its blocker and exact evidence.
- Work the improvement queue: research, build, maintain, repair, consolidate redundant jobs, run experiments. Routine and reversible without asking. At least once per day when a tick has capacity, take the highest-value accessible item, do it, verify the actual result, and write the result plus a concrete next step or blocker.
- End every tick with a short report as the run's final message. Use exact outcome words per check: `checked` with `no_findings` or the findings listed; `skipped` (with reason); `read_failed` (with the blocker); `blocked` (with what is needed). Record what actually happened, not what was attempted.
- Dedupe and issue state: every transition goes through the state helper (`observe`, `attempt`, `report`, `release_report`, `confirm_report`, `resolve`, `reopen`, `status`). The helper owns attempt bookkeeping and backoff (1h, 4h, 12h, 24h cap), fingerprint suppression, atomic locked writes, and corrupt-state preservation. Never hand-edit the state file. A check that could not read its source is `read_failed`, never "no findings".
- Bounded retries: inside one tick, retry a failed read/action at most twice with backoff, then stop and record the blocker. Across ticks, the helper computes the next retry; never retry on a fixed cadence without new information.
